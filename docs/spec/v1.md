# DCABSM V1 specification

DCABSM (DocCyblade's Actual Budget Server Manager) is a command-line tool that installs and maintains several Actual Budget servers on one Host. This document specifies V1. Capitalised terms, such as Release, Instance and Regroup, are defined in [GLOSSARY.md](../../GLOSSARY.md). The reasons behind the larger choices are in [docs/adr/](../adr/). Command syntax, prompts and messages are in [docs/cli.md](../cli.md), and work left for later is in [docs/roadmap.md](../roadmap.md).

Each numbered section below is meant to become one or more implementation tickets.

## 1. Scope

### 1.1 Audience

Technically comfortable self-hosters running one Host, with the author as the first user. One System Admin runs every command, as root.

### 1.2 What V1 does

- Host setup, and a doctor that checks and fixes the Host.
- Release management: install, list, remove unused Releases, and install Node patches.
- Instances: create, remove (with a final Backup), start, stop, restart, list, show, logs, change hostname, reset a password, and view and change a fixed list of Instance settings.
- Upgrade, with a Pre-upgrade backup and automatic rollback on failure. Rollback on request.
- Backup, Restore and Clone of whole Instances.
- Scheduled backups in a Nightly run, with Retention.
- Certificate test and update.
- A check for new Releases, Node patches and DCABSM versions.
- Installing and updating DCABSM itself, with signed tarballs.
- bash Tab completion.

### 1.3 Shape

- CLI only. There is no web UI.
- DCABSM manages only the Host it runs on.
- Actual is installed natively from npm and run by systemd. There is no Docker.
- Each Instance has its own hostname on port 443 through Nginx. Actual listens on `127.0.0.1` only, on its own port, over plain HTTP.
- Browsers must reach an Instance over HTTPS on a real hostname, because Actual's client needs a secure context. Actual doesn't enforce this itself.
- Certificates are brought by the System Admin. DCABSM can make a self-signed one instead.
- DCABSM works on whole Instances only, never on single Budget files. Moving one Budget file is done with Actual's own export and import.

### 1.4 Supported Hosts

The supported OS list is one table in the code. Adding an OS is one entry, allowed only once it passes the OS gate (13.6). The README's list comes from this table.

| OS | Architectures | Form |
|---|---|---|
| Debian 13 | amd64, arm64 | any install |
| Ubuntu 24.04 LTS | amd64, arm64 | any install |
| Ubuntu 26.04 LTS | amd64, arm64 | any install |
| TurnKey Core 19.x (Debian 13) | amd64 | from the ISO |
| TurnKey Node.js 19.x (Debian 13) | amd64 | from the ISO |

- amd64 is tested on a real Host: Debian 13, Ubuntu 24.04 and Ubuntu 26.04 VMs, and both TurnKey appliances.
- arm64 is built and CI-tested, but not tested on a real Host. It becomes fully supported once an arm64 VM passes the OS gate (13.6). TurnKey publishes no arm64 images.
- Virtual machines and bare metal only. The Proxmox VE host itself and containers (LXC, WSL, Docker, Podman) are refused, see 10.3. That includes TurnKey's LXC templates.
- TurnKey appliances other than Core and Node.js are refused (10.7).
- DCABSM is designed for a fresh, dedicated Host. Installing on a server that already runs other things may hit deliberate refusals.
- Only the distro's `nginx` package is supported. On TurnKey that is Debian's.
- The OS is read from `/etc/os-release`, never from `dpkg-vendor`, which reports `TurnKey` on a TurnKey appliance.

### 1.5 Supported Releases

- Stable Actual versions from npm only: `@actual-app/sync-server` versions matching `^\d+\.\d+\.\d+$`.
- 26.10.0 or newer. The floor is one constant in the code, so it can be raised. From 26.10.0 no compiler or GitHub download is needed on amd64 or arm64.
- No Releases built from source, and no nightly Releases.
- There is no list of tested versions. Any stable Release at or above the floor is allowed.

## 2. On-Host layout

DCABSM keeps no registry or database. The filesystem is the only record ([ADR-0001](../adr/0001-filesystem-is-the-only-record.md)):

- The Instance list is the contents of `/srv/dcabsm/instances/`.
- The Release list is the contents of `/srv/dcabsm/releases/`.
- An Instance's Release is whatever its `release` symlink points to.
- Unfinished work uses dot-prefixed names, such as `.installing-26.11.0`, which every listing ignores.
- `/run/lock/dcabsm.lock` stops two DCABSM commands changing state at once.

### 2.1 Paths

Paths are fixed. The only exception is the backup directory, which the `backupDir` Host setting can move at setup.

```
/opt/dcabsm/<ver>/                     DCABSM itself, current and previous version only
/usr/local/bin/dcabsm -> /opt/dcabsm/<ver>/bin/dcabsm
/usr/share/bash-completion/completions/dcabsm

/etc/dcabsm/dcabsm.json                Host settings, layout version, owned-file hashes, Unsupported Host mark
/etc/dcabsm/replaced/<timestamp>/      old copies of owned files that DCABSM replaced

/etc/systemd/system/dcabsm@.service    template unit for every Instance
/etc/systemd/system/dcabsm-nightly.timer
/etc/systemd/system/dcabsm-nightly.service
/etc/nginx/conf.d/dcabsm.conf          includes instances/*/nginx/vhost.conf
/etc/nginx/conf.d/dcabsm-default.conf  catch-all, only if nothing else is the 443 default

/srv/dcabsm/node/<version>/            Node runtimes
/srv/dcabsm/node/<major> -> <version>  newest patch of each major
/srv/dcabsm/releases/<version>/        read-only, with package-lock.json kept
/srv/dcabsm/acme/                      shared ACME webroot
/srv/dcabsm/update-check.json          last `host check-updates` result, read by `instance list`
/srv/dcabsm/backups/<name>/            default backup directory
/srv/dcabsm/backups/<name>.removed-<UTC time>/
/srv/dcabsm/instances/<name>/
  release -> /srv/dcabsm/releases/<version>
  .changing-release                    only while a Release change or restore is under way
  config/instance.json                 Instance record
  config/config.json                   generated, never edited by hand
  data/                                ACTUAL_DATA_DIR, holds .migrate
  server-files/
  user-files/
  nginx/
    vhost.conf                         generated, never edited by hand
    cert.pem                           full chain
    key.pem
```

Every path is set explicitly in the unit and in `config.json`, because Actual's defaults change if `/data` exists on the Host.

### 2.2 Ownership

`doctor` checks this table and fixes it.

| Path | Owner:group | Mode |
|---|---|---|
| `/etc/dcabsm/`, `dcabsm.json` | `root:root` | 700, 600 |
| `/srv/dcabsm/`, `releases/`, `instances/` | `root:root` | 755 |
| `releases/<version>/` | `root:root` | read-only, world-readable |
| `acme/` | `root:root` | 755 |
| `backups/` and archives | `root:root` | 700, 600 |
| `instances/<name>/`, `config/` | `root:dcabsm-<name>` | 750 |
| `config/config.json` | `root:dcabsm-<name>` | 640 |
| `config/instance.json` | `root:root` | 600 |
| `data/`, `server-files/`, `user-files/` | `dcabsm-<name>` | 700 |
| `nginx/` | `root:root` | 700, files 600 |

The Instance account can read `config/`, so the private key lives in `nginx/`, which it can't read. Nginx loads those files as root. The Instance account can't write to the Instance directory or `config/`, so it can't repoint its own `release` symlink.

`instances/` and `releases/` are world-readable so that Tab completion can list them without root.

### 2.3 Host settings

`/etc/dcabsm/dcabsm.json` holds:

- the layout version (see 11.4)
- `backupDir`, set at setup
- the Nightly run time, default `03:30` Host local time
- the Retention count for each kind (see 8.3)
- a hash of each owned file DCABSM last wrote (see 10.5)
- the Unsupported Host mark, once any override has been used (see 10.4)

`host settings` shows them and `host set <key> <value>` changes one. The keys are `nightly-time` and `keep-<kind>`.

## 3. Releases and Node runtimes

### 3.1 Installing a Release

1. Take the lock.
2. Read the version's `engines.node` from the npm registry. npm doesn't enforce `engines`, so DCABSM must.
3. Choose the Node runtime: the newest LTS major that satisfies `engines.node` and is no newer than DCABSM's Node ceiling. The ceiling is a constant in the code, and a DCABSM release raises it only after the container layer (13.1) passes on that major, because `engines` is only a floor and Actual tests upstream on one major. There is no override. If no major fits, refuse the Release and point to `self update`. Install the runtime if missing (3.3).
4. Install with npm `--save-exact --ignore-scripts` into `releases/.installing-<version>/`, using that Node. `--ignore-scripts` means no dependency's install script runs as root.
5. Keep `package-lock.json`. Transitive dependencies float, so the lockfile is what pins them.
6. Confirm that `bcrypt`, `argon2` and `better-sqlite3` load. Refuse the Release and delete the temporary directory if they don't.
7. Rename into `releases/<version>/` and make it read-only.

The link between a Release and its Node major is recorded with the Release when it is installed and never changes.

A Release is only safe to share between Instances because every Instance sets its data paths explicitly. With them set, Actual writes nothing inside the Release directory.

### 3.2 Removing unused Releases

`release prune` removes every Release that no `release` symlink points to and no `.changing-release` marker names (6.6), and every Node runtime that no remaining Release uses. It lists them and confirms, unless `--yes`. DCABSM's own Node is not a managed runtime, so pruning can never break DCABSM.

A Release removed as unused can be reinstalled from npm later, for example by `instance rollback`, but its dependencies may differ, because its lockfile went with it.

### 3.3 Node runtimes

Each Release carries its own Node ([ADR-0002](../adr/0002-each-release-carries-its-node.md)).

- DCABSM downloads official tarballs from nodejs.org into `/srv/dcabsm/node/<version>/`, checked against `SHASUMS256.txt` and its signature with `gpgv`. DCABSM ships Node's release signing keys as a binary keyring at `share/node-release-keys.gpg` inside its own version directory, `/opt/dcabsm/<ver>/`, so they change only with a new DCABSM version.
- The tarballs are `.tar.xz`, so unpacking needs `xz-utils`. `host setup` installs it (10.2), because TurnKey Core does not ship it.
- `node/<major>` links to the newest installed patch of that major.
- An Instance runs the Node of its Release. The unit's `PATH` puts that Node first.
- DCABSM never installs, changes or uses the system's Node, so it coexists with any Node already on the Host.
- Rollback returns to the old Node automatically, because it returns to the old Release.
- Moving to a new Node major happens through a normal Upgrade to a Release that needs it.

### 3.4 Node patches

Node security patches don't come from apt. `doctor`, `instance list` and `host check-updates` report a newer patch for an installed major, and a major that is end of life.

`release update-node` installs the patch, after confirming, repoints `node/<major>` and restarts the affected running Instances one at a time. It skips an Instance with a `.changing-release` marker and names it.

Before it repoints, it checks that every installed Release on that major still loads its native modules with the new Node, by loading them with that Node. `doctor` makes the same check for every Release. A Release that fails is reported, and `update-node` does not repoint until it passes.

### 3.5 Checking for updates

`host check-updates` is the only command that uses the network to check for updates. It reports:

- a newer stable Actual Release
- a newer Node patch for each installed major
- a newer DCABSM version

`instance list` shows the result of the last check underneath its table.

## 4. Instances

### 4.1 Names

- Instance names match `^[a-z][a-z0-9-]{0,23}$`. This leaves room for `dcabsm-<name>` within Linux's 32-character username limit, and a name can never contain a dot.
- A name is fixed at creation and separate from the hostname. Cloning and then removing the original acts as a rename.

### 4.2 Instance account

- Each Instance runs as its own static system account, `dcabsm-<name>`, with a matching group, no login shell and no home directory.
- The account is created with the Instance and deleted with it, after the final Backup.
- Ownership is always set from the account name, on create, restore and clone, so it never relies on UIDs matching. A reused name gets a new account.
- `DynamicUser=` is not used: it recycles UIDs and doesn't fit the layout.

### 4.3 Ports

- An Instance's port is the first port from 15127 upward that isn't in any Instance record and isn't listening on the Host. 15127 is a constant, with no setting and no per-Instance choice.
- A port stays with its Instance until removal and can then be reused. A clone gets a new port.

### 4.4 Instance record and `config.json`

The Instance record, `config/instance.json`, holds the port, hostname, `scheduledBackups` (on or off, default on), `createdAt` (when `instance create` made it; an Instance from before it was recorded has none) and the Instance settings the System Admin set (4.11). It holds nothing for a setting left at its default.

`config.json` is generated from the record for the Instance's current Release, because Actual's strict validation refuses to start on a key it doesn't know, so a key for a newer Release would stop an older one starting. It always sets:

- `dataDir`, `serverFiles` and `userFiles`, explicitly
- `hostname: "127.0.0.1"` and the port
- `trustedProxies: ["127.0.0.1/32"]` (see 5.4)
- `allowedLoginMethods: ["password", "openid"]` and `trustedAuthProxies: []`, which with the vhost's header stripping (5.2) rule out Actual's header login. Behind Nginx, header login would trust a header any client can send.

It then adds each Instance setting from the record that the current Release knows, and leaves out every other key, so the Release's own defaults apply. It never writes `openId.*` ([ADR-0005](../adr/0005-openid-belongs-to-actual.md)).

It is regenerated on every Release change, restore and setting change. `doctor` flags a `config.json` that differs from what DCABSM would generate, and `doctor --fix` regenerates it and asks separately whether to restart.

### 4.5 The unit

One template unit, `dcabsm@.service`, runs every Instance:

- `ExecStart` runs `/srv/dcabsm/instances/%i/release/node_modules/.bin/actual-server --config /srv/dcabsm/instances/%i/config/config.json`.
- `ACTUAL_DATA_DIR=/srv/dcabsm/instances/%i/data`, `NODE_ENV=production`, and `WorkingDirectory` set to the Instance directory.
- `PATH` puts the Release's Node runtime first.
- `ConditionPathExists=!/srv/dcabsm/instances/%i/.changing-release`, so a reboot can't start a half-changed Instance. A second `ConditionPathExists=/srv/dcabsm/instances/%i/release/node/bin/node` stops the unit starting on whatever `node` the Host has when the Release's Node is missing. The start is skipped, and verification (6.2) and doctor report it.
  Every Release change, restore and rollback starts the Instance while the marker exists. For that start only, DCABSM lifts the marker rule with a runtime drop-in, `/run/systemd/system/dcabsm@<name>.service.d/10-start-gate.conf`. It clears the `ConditionPathExists` rules and puts the Node rule back. It is removed when the start and verification end, and the boot wipes `/run`, so a reboot mid-change still finds the rule in force.
- `Type=simple`, and an `[Install]` section with `WantedBy=multi-user.target`. The `[Install]` section is what lets `systemctl enable` work, which Setup, `instance start` and Upgrade rely on. The unit doesn't wait for `network-online.target`, because Actual sits behind local Nginx and needs no network at boot.
- `Restart=on-failure`, `RestartSec=5`, `StartLimitBurst=3` and `StartLimitIntervalSec=300`, constants. A crash restarts Actual, but a server that refuses its data (6.4) ends failed after three tries instead of looping. Verification (6.2) treats a unit that restarted during its window as failed. Every start or restart the Manager makes itself first runs `systemctl reset-failed`, so a run of deliberate stops and starts never trips the limit. Crashes get no reset, so a crash loop still does.

A unit per Instance was rejected because fixes would spread across files, and systemd doesn't allow a variable as the program in `ExecStart`.

The unit adds this sandbox, tested with nothing removed:

```
User=dcabsm-%i
Group=dcabsm-%i
UMask=0077
NoNewPrivileges=yes
CapabilityBoundingSet=
ProtectSystem=strict
ReadWritePaths=/srv/dcabsm/instances/%i/data /srv/dcabsm/instances/%i/server-files /srv/dcabsm/instances/%i/user-files
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
ProtectClock=yes
ProtectHostname=yes
ProtectProc=invisible
RestrictNamespaces=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
LockPersonality=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
SystemCallArchitectures=native
SystemCallFilter=@system-service
```

- `MemoryDenyWriteExecute=` stays off, because V8 generates code at runtime.
- Outbound network stays open, for bank sync.
- There is one unit and no relaxed sandbox, because containers aren't supported.

### 4.6 Create

`instance create <name> --hostname <host> (--cert <f> --key <f> | --self-signed) [--release <v>] [--yes]`

1. Take the lock. Check the name (4.1).
2. Check the hostname is a valid lowercase DNS name, with no wildcard and no trailing dot. Refuse one already used by another Instance or found in `nginx -T`, because Nginx only warns about duplicates.
3. Get a certificate (5.5). With neither `--cert`/`--key` nor `--self-signed`, prompt on a terminal and refuse otherwise.
4. Use `--release`, or the newest installed Release. Install it first if missing.
5. Create the account, assign the port, and create every Instance directory before the first start. Actual's folder migration ignores directories that already exist, so `server-files/` and `user-files/` can sit outside `data/`.
6. Write the record, `config.json`, `vhost.conf` and the certificate files. Run `nginx -t` and reload.
7. Start and verify (6.2), and enable the unit.
8. Offer the first password. On a terminal and without `--yes`, ask `Set the server password now? [Y/n]`. Yes hands the terminal to the same tool as `instance reset-password` (4.10), run the same way, so DCABSM never sees the password. With no terminal or with `--yes` nothing is asked. A new Instance is never OpenID-only, so there is no OpenID check.

A failure at `nginx -t` removes everything made. A failed start or Verification after the Nginx reload keeps the Instance (account, directory and vhost), exits 1 and names `instance logs`, `instance start` and `instance remove`. It says so when the Release's Node is missing on disk.

**The first visit sets the password.** Until someone sets the server password in Actual, the first person to reach the hostname sets it. Unless step 8 set it, the result says so and says to open the hostname at once. Declining the offer, or a reset that fails or is aborted, does not fail `create`: the Instance is fine, so the command exits as it would without the offer and keeps that warning. The README advises creating the Instance before DNS points at the Host, or setting the password straight away.

### 4.7 Remove

`instance remove <name>` confirms by typing the name.

1. Stop the Instance.
2. Take a `final` Backup. An Instance that has never started has no data, so it takes none, and the result says so.
3. Rename `backups/<name>/` to `backups/<name>.removed-<UTC time>/`.
4. Remove the vhost, run `nginx -t` and reload.
5. Delete the Instance directory and the account.

A reused name starts with no Backups. Deleting `.removed-` folders is a Manual System Admin task, and `doctor` lists them with their size.

### 4.8 Start, stop, restart, list, show and logs

- `instance start|stop|restart <names>|--all` wraps `systemctl` for `dcabsm@<name>`. `stop` also disables the unit and `start` enables it, so a stopped Instance stays stopped across a reboot, as Upgrade, restore and the Nightly run already assume. `restart` doesn't change it. A stopped Instance keeps its vhost and shows Nginx's 502. There is no maintenance page.
- `instance list` is the overview: one row per Instance with state, Release, hostname, port, certificate days left and last scheduled Backup, then the last `host check-updates` result. It also shows an Unsupported Host mark and any `.changing-release` marker. There is no separate status command.
- `instance show <name>` shows one Instance in detail.
- `instance logs <name> [-f] [--since <time>]` reads the unit's journal. Logs stay in journald.

### 4.9 Change hostname

`instance set-hostname <name> <host> [cert options]` needs a certificate covering the new name. It applies the same hostname checks as create, and follows the certificate update steps (5.6). Actual doesn't restart. Actual's OpenID settings still name the old hostname, so OpenID login fails on the new one until the System Admin updates them in Actual and the provider's redirect URL. The result says so.

### 4.10 Reset a password

`instance reset-password <name>` runs `actual-server --config <path> --reset-password` from the Instance's own Release, as the Instance account through `runuser`, against the Instance's data, with the terminal handed over, so DCABSM never sees the password.

- It refuses when there is no TTY, on an Instance that has never started, and on an OpenID-only Instance, where Actual has no password to change.
- Never started means `server-files/account.sqlite` doesn't exist yet, because Actual creates it and runs its migrations only when the server starts. OpenID-only means Actual's `auth` table, read from that file, has an `openid` row and no `password` row (ADR-0005).
- On a started Instance that has no password yet, the same tool sets the first one.
- It prints one line first: if you paste a password, press Enter separately.

### 4.11 Instance settings

DCABSM's code holds a fixed list of the Actual settings an Instance exposes. Each entry has a DCABSM key, Actual's key, a type, a check and the first Release that knows it.

| DCABSM key | Actual key | Actual default | Check | First Release |
|---|---|---|---|---|
| `upload-sync-limit-mb` | `upload.fileSizeSyncLimitMB` | 20 | whole number 1–1024 | 26.10.0 |
| `upload-encrypted-sync-limit-mb` | `upload.syncEncryptedFileSizeLimitMB` | 50 | whole number 1–1024 | 26.10.0 |
| `upload-limit-mb` | `upload.fileSizeLimitMB` | 20 | whole number 1–1024 | 26.10.0 |
| `openid-enforce` | `enforceOpenId` | false | `true` or `false` | 26.10.0 |
| `openid-user-creation` | `userCreationMode` | manual | `manual` or `login` | 26.10.0 |
| `simplefin-allowed-networks` | `simplefinAllowedNetworks` | empty | comma-separated IPs and CIDRs | 26.11.0 |

- Any other key is refused as "unknown setting". Keys DCABSM always sets (4.4) can never be set.
- Never settable: `loginMethod` (password and OpenID are switched in Actual's UI), `https.*` (Nginx handles TLS), `webRoot`, `env`, `mode` and `projectRoot`.
- There are no secret settings in V1, so `config.json`, which the Instance account can read, needs no special handling.

**OpenID is set up in Actual's web UI** ([ADR-0005](../adr/0005-openid-belongs-to-actual.md)). Actual stores it, client secret included, in `server-files/account.sqlite`. If config set it, Actual would overwrite that row on every start, but removing it from config would leave the row, so two places would each claim to be in charge. The redirect URL to register at the provider is `https://<hostname>/openid/callback` (Actual's OpenID documentation). Backups and Clones carry OpenID because they carry `server-files/`.

**Commands:**

- `instance settings <name>` shows each setting with its DCABSM key, Actual's key, its value, whether that is Actual's default or set by the System Admin, and whether the current Release uses it. Defaults come from the Release's schema, or from DCABSM's table when that can't be read.
- `instance set <name> <key> <value> [--yes]` changes one setting.
- `instance unset <name> <key> [--yes]` returns one to Actual's default, whatever the Release.
- `instance create` has no settings flags. `backup schedule` (8.2) stays under `backup`.

**After a change.** `set` and `unset` take the lock, refuse while a `.changing-release` marker exists (6.6), write the record and regenerate `config.json`. Actual reads its config only at startup, so:

- on a terminal it asks "Restart <name> now? [Y/n]"
- `--yes` restarts without asking
- with no terminal and no `--yes`, it reports "restart needed"
- a stopped Instance isn't started, and the output says the change applies on the next start

After an upload-limit change, `vhost.conf` is regenerated for the new `client_max_body_size` (5.2), passes `nginx -t` and Nginx reloads at once. If `nginx -t` fails, the old `vhost.conf` goes back.

**Settings a Release doesn't know.**

- `instance set` refuses a key the current Release doesn't know, naming the first Release that does, for example "needs 26.11.0, <name> runs 26.10.0".
- After a rollback, a restore, or a restore from an archive on an older Release, the record keeps the setting and `config.json` leaves it out. `instance settings`, `instance show` and the rollback and restore output say "not used by <release>". A later Upgrade brings it back with no action needed.
- `instance show` lists the settings the System Admin set and any that aren't used. `host doctor` reports unused settings as a note.

**Clone and restore.** A Clone takes the source's settings, because it is restored from the source's archive, Instance record included. A restore in place keeps the current record and its settings (7.4). A restore onto a new Host takes the archive's record (7.7).

### 4.12 Known limit

One Instance can reach another's localhost port. Isolation covers files and processes, and Actual's own login protects each port.

## 5. Nginx and certificates

### 5.1 Files

DCABSM never edits a file in `/etc/nginx` that it didn't create. It writes `conf.d/dcabsm.conf`, which includes every `instances/*/nginx/vhost.conf`, and `conf.d/dcabsm-default.conf` (5.3). `conf.d/*.conf` is the one include shared by every distro package.

### 5.2 The vhost template

The template is the same for every Instance, with no per-Instance Nginx options and no custom snippets. `doctor` flags a `vhost.conf` that differs from what DCABSM would generate.

- TLS 1.2 and 1.3 only.
- IPv4, plus IPv6 when the Host has it.
- HTTP/1.1 only. There is no HTTP/2, which also avoids `http2` syntax that differs between the supported Nginx versions.
- `proxy_http_version 1.1`, with `Connection ""`, `Host`, `X-Forwarded-For $remote_addr` and `X-Forwarded-Proto`. Actual uses no WebSockets, so there are no `Upgrade` headers.
- `proxy_set_header X-Actual-Password "";`, so a client can never reach Actual's header login (4.4).
- No `add_header` for `Cross-Origin-Opener-Policy` or `Cross-Origin-Embedder-Policy`, because Actual sets them and they pass through once each.
- No HSTS, because it would stop a self-signed certificate being clicked through and is hard to undo in browsers.
- `client_max_body_size` is the largest of the Instance's Actual upload limits plus 1 MB. With Actual's defaults that is `51m`.
- Port 80 redirects each hostname to HTTPS, except `/.well-known/acme-challenge/`, which is served from `/srv/dcabsm/acme/`, so a System Admin running certbot with `--webroot` can renew. Port 80's default site is left alone.

### 5.3 Catch-all

Without a default server on 443, an unknown hostname or bare IP gets the first Instance's certificate and app. DCABSM adds `dcabsm-default.conf`, with TLS 1.2 and 1.3 and `ssl_reject_handshake on`, unless another default server already exists on 443.

If one does, DCABSM skips the file and `doctor` reports that the other site decides the TLS versions offered. A second default fails `nginx -t`, so if the System Admin adds their own later, deleting `dcabsm-default.conf` clears the conflict.

### 5.4 Client addresses

`config.json` always sets `trustedProxies: ["127.0.0.1/32"]`. Without it, Actual sees every login as coming from Nginx, and five failed logins by anyone lock everyone out of that Instance for 15 minutes, even with the right password. `X-Forwarded-For $remote_addr` replaces anything the client sent, so a forged header doesn't escape the limit. The setting exists from 26.10.0.

### 5.5 Every Instance always has a certificate

One missing certificate fails `nginx -t` for the whole Host and blocks every reload, so that state must never exist.

- Every Instance holds its own copy of its certificate and key, even when several use the same wildcard. There is no shared certificate, so each Backup stays self-contained.
- `--self-signed` makes an ECDSA P-256 certificate with `openssl`, valid for 397 days. DCABSM then tells the System Admin that browsers warn on each device, and may warn again later, that Actual works after proceeding, and that offline use and installing as an app need a certificate the device trusts, because the service worker won't register on a clicked-through certificate. It suggests bringing a real certificate later with `cert update`.

### 5.6 Certificate update

`cert update <names>|--all --cert <f> [--key <f>]`. `--all` means every Instance. Actual doesn't restart. A certbot deploy hook can run it.

1. Take the lock and validate every named Instance first, with `node:crypto`. Refuse an expired or not-yet-valid certificate, a hostname mismatch, a key that doesn't match, or a passphrase-protected key, with no override. Any refusal stops the command with nothing changed. An untrusted chain only warns, because private CAs are normal for this audience.
2. Without `--key`, check the current key against the new certificate.
3. Keep the old files, swap in the new ones, run `nginx -t` and reload.
4. Connect to `127.0.0.1:443` with the hostname and confirm the served fingerprint within 5 seconds.
5. On any failure, restore the old files, reload if a reload already happened, and exit non-zero.

### 5.7 Certificate test

`cert test [<names>|--all]` probes what is served, by connecting to `127.0.0.1:443` with the hostname. It reports days left, hostname match, whether the served certificate matches the file on disk, whether system CAs trust it, and whether the hostname resolves.

- Expired, mismatched or unreachable is a failure and exits non-zero.
- Under 30 days left, or a hostname that doesn't resolve, is a warning.
- Untrusted is a note.

`doctor` runs the same test for every Instance, and `instance list` shows days left.

## 6. Upgrade and rollback

### 6.1 Upgrade

`instance upgrade <names>|--all [--to <v>] [--yes]`. One outage covers the Backup and the switch:

1. Take the lock.
2. Preflight: show from and to with a link to the release notes and confirm unless `--yes`. Then install the target Release if missing, check `engines`, and check free space for a Backup. A refusal here changes nothing, and nothing is installed if the answer is no.
3. Stop the Instance.
4. Take the Pre-upgrade backup. It can't be skipped.
5. Write the `.changing-release` marker.
6. Repoint `release` and regenerate `config.json`.
7. Open the start gate (4.5), start, verify (6.2), close the gate and remove the marker.

A failure before the symlink moves restarts the Instance on its old Release, with nothing changed.

- **Target.** The default is the latest stable version on npm. `--to <version>` picks another. If npm can't be reached, the command fails and asks for `--to` with an installed Release. `upgrade` refuses an older target and points to `instance rollback`.
- **Several Instances.** It runs one at a time, confirms the whole list once, stops at the first failure, leaves the rest untouched and ends with a summary.
- **Stopped Instances.** A stopped or failed Instance upgrades normally, including the start and verification, because migrations only run at start. It then returns to stopped.
- **Never started.** An Instance that has never started has no data, so it just changes Release, with no Backup or verification.
- **Devices.** The result says that open devices show Actual's update banner: click Update now, or reload twice.

### 6.2 Verification

Within 120 seconds, a constant, the unit is active, `GET /health` returns `{"status":"UP"}` and `GET /info` reports the target version. Every Release change, rollback and restore uses this check.

`/health` proves only that the process is listening, not that data is readable. These routes aren't documented by Actual as a public API.

### 6.3 Failed upgrade

DCABSM rolls back automatically: it restores data from the Pre-upgrade backup, repoints `release` to the old Release and verifies it. This loses nothing, because the Instance was stopped from the Backup until then, and it needs no Regroup and no device action.

If that also fails, the Instance stays stopped, the Backup is kept and named, and the command exits non-zero. It never retries in a loop. There is no flag to turn the automatic rollback off.

### 6.4 Why rollback can't always keep data

An older Actual server refuses to start on data with server migrations it doesn't know. It exits 1 and changes no file. Actual's `down` migrations must never be used, because they delete every budget. Budget file migrations run in the client, and browsers keep their own copies.

### 6.5 Rollback on request

`instance rollback <name> [--restore-data] [--yes] [--confirm <name>]` goes one step back, to the Release recorded in the Instance's newest Pre-upgrade backup, and keeps current data by default.

1. Take the lock. Stop, write the marker, repoint `release`, regenerate `config.json`, start and verify.
2. On any failure, return to the newer Release, start and verify it. The data hasn't changed.
3. Report what happened and point to `--restore-data`.

`--restore-data` first takes a `pre-restore` Backup, shows the Pre-upgrade backup's date, asks for the Instance name to be typed, then restores that Backup as in 7.4, including the Regroup and the device advice. Data is only ever lost on this deliberate path.

- If the newest Pre-upgrade backup already matches the current Release, there is nothing to roll back, and the command points to `instance restore`.
- `--yes` answers the plain `Continue?` prompt. `--confirm <name>` answers the typed-name prompt, and `--restore-data` always needs it: `--yes` alone never allows a data restore.
- There is no general downgrade.
- A target Release removed as unused is reinstalled from npm.
- `rollback` handles one Instance at a time.
- The result tells devices to click Update now or reload twice, as after an Upgrade.
- The result names any Instance setting the old Release doesn't know as "not used by <release>" (4.11).

### 6.6 Interrupted changes

The lock doesn't survive a reboot, so the `.changing-release` marker sits in the Instance directory. It records the operation (upgrade, rollback or restore), the from Release, the to Release, the Backup path, and whether data is being restored. A restore or `rollback --restore-data` also records the archive it reads, so the restore can be repeated; a marker without it makes recovery refuse and name the manual restore command.

- While it exists, `instance list`, `instance show` and `doctor` report it, and every changing command for that Instance refuses except `instance rollback`.
- The unit's `ConditionPathExists` keeps the Instance from starting at boot.
- `rollback` after an interrupted Upgrade restores from the Backup and returns to the from Release. It does not Regroup, for the same reason as the automatic rollback in 6.3: the data goes back to what the from Release wrote, so its files already match.
- `backup prune --all` skips an Instance with a marker, with a warning, so the Backup the marker names is not deleted. Pruning that Instance by name refuses.
- After an interrupted restore, it repeats the restore.
- After an interrupted rollback that was keeping data, it returns to the marker's to Release and keeps the data.

## 7. Backup, restore and clone

### 7.1 The archive

- One `.tar.gz` per Backup, made with GNU tar, holding the whole Instance directory apart from the `release` symlink: `config/`, `data/`, `server-files/`, `user-files/` and `nginx/`, with the Instance certificate and key.
- `manifest.json` comes first. It records `format: 1`, the Instance name, kind, UTC time, Release, Node runtime, DCABSM version and hostname. The Node runtime is for information only: a Release reinstalled on restore gets its Node from 3.1.
- DCABSM reads every older format for good. It refuses an archive with a newer format and tells the System Admin to run `self update`.
- Archives are `root:root` 600 in 700 directories.

**Archives are not encrypted in V1.** They hold every budget, every login and the Instance's private key, plus what Actual itself stores in plain text in `server-files/`: the OpenID client secret and bank-sync credentials. So they are as sensitive as the Host's root account. A password would have to be stored on the Host for scheduled Backups, right beside the archives. Encryption comes with off-Host backup targets on the roadmap.

### 7.2 Names and kinds

Archives are named `<UTC time>-<kind>-<release>.tar.gz` in `backups/<name>/`, for example `20261107T031500Z-pre-upgrade-26.11.0.tar.gz`, so rollback and Retention work from a directory listing. The manifest repeats these facts.

| Kind | Taken by |
|---|---|
| `manual` | `backup create` |
| `scheduled` | the Nightly run |
| `pre-upgrade` | `instance upgrade` |
| `pre-restore` | `instance restore` and `instance rollback --restore-data` |
| `pre-clone` | `instance clone`, of the source |
| `final` | `instance remove` |

### 7.3 Taking a Backup

Every Backup stops the Instance, because SQLite's online backup can't keep `account.sqlite`, the group files and `user-files/` consistent with each other.

1. Take the lock. Check free space before stopping, and fail with a clear error if there isn't enough.
2. Say that the Instance will be down for a few seconds. Stop it.
3. Write the archive under a dot-prefixed temporary name, check it by listing it back, then rename it into place.
4. Start the Instance again. A stopped Instance is archived without being started.

`backup create <names>|--all` runs one Instance at a time, so only one is down at once. It carries on past a failure and ends with a summary. `backup list [<names>]` lists archives.

### 7.4 Restore in place

`instance restore <name> [<archive>]` defaults to the newest archive in `backups/<name>/`. A path picks any archive.

1. Take the lock. Confirm by typing the Instance name, and show the device advice below.
2. Take a `pre-restore` Backup.
3. Write the `.changing-release` marker.
4. Replace `data/`, `server-files/` and `user-files/`. Move the Instance to the archive's Release, installing it if missing. Set ownership from the account name. Regroup (7.5).
5. Regenerate `config.json` and `vhost.conf`, start and verify (6.2), and remove the marker.

It keeps the current Instance record, hostname, port, Instance settings and Instance certificate, so a restore can't bring back an expired certificate or an old hostname. The result names any Instance setting the archive's Release doesn't know as "not used by <release>" (4.11).

If verification fails, DCABSM restores the `pre-restore` Backup automatically, as after a failed Upgrade. A stopped Instance returns to stopped afterwards. The result suggests an Upgrade if the System Admin wants the newer Release back.

### 7.5 Regroup

Every restore regroups ([ADR-0004](../adr/0004-every-restore-regroups.md)). DCABSM gives each Budget file a new group id in `account.sqlite` and renames its `group-<id>.sqlite` to match, keeping every message.

- Without it, the first device that opens the app re-sends every change made after the Backup, and the restore is silently undone.
- With it, each device shows Actual's "Syncing has been reset on this cloud file" dialog, and **Revert** brings it exactly to the restored data. Choosing "upload this file to be the latest version" would undo the restore.
- It applies to `instance restore`, `instance rollback --restore-data` and `instance clone`. The one exception is the automatic rollback after a failed Upgrade (6.3).
- DCABSM depends on Actual's `account.sqlite` schema and group file naming, so a Release that changes them needs a matching DCABSM change.

### 7.6 Device advice

DCABSM can't see devices, so it can only advise. Every restore, and `rollback --restore-data`, says:

- Before a planned restore, open Actual on every device and let it sync. Anything a device hasn't synced is lost when it clicks Revert.
- Changes made after the Backup are gone on every device.
- After the restore, each device shows Actual's reset dialog. Click **Revert**, never "upload this file to be the latest version".
- A Budget file created after the Backup comes back if a device registers it again.
- Actual doesn't document or support restoring a server from its files, so this restore is DCABSM's own approach. Device behaviour was tested in Chromium only.

### 7.7 Restore onto a new Host

`instance restore --from <archive>` recreates an Instance from an archive when no Instance of that name exists. It covers disaster recovery. It keeps the archive's record as it was, including `scheduledBackups`.

- It takes the Instance name from the archive, with no override. If that name exists, it refuses and points to `instance restore <name> <archive>` or `instance clone --from`.
- It keeps the archive's Instance record, hostname, Instance settings and certificate. It takes a new port if the archived one is in use. An expired certificate is kept with a warning pointing to `cert update`, never refused, so disaster recovery isn't blocked.
- It creates the account, sets ownership from its name, applies the same hostname check as create, regroups, regenerates `config.json` and `vhost.conf`, and passes `nginx -t` before reloading.
- It installs the archive's Release if missing.
- A path given where a name belongs is refused, with a pointer to `--from`.

### 7.8 Clone

`instance clone <source> <new> --hostname <host> [cert options]`:

1. Stop the source briefly, take a `pre-clone` Backup of it (kept in the source's Backups), and start it again.
2. Restore that archive into the new Instance, which gets its own account, a new port, the given hostname, and the source's Release and Instance settings, including whether scheduled Backups are on (`scheduledBackups` is copied from the archive's record, so a clone of an Instance with no schedule has none).
3. Regroup.

`instance clone --from <archive> <new> --hostname <host> [cert options]` clones from an archive and takes no Backup.

- The certificate is the source's only if it covers the new hostname. Otherwise the clone needs `--cert`/`--key` or `--self-signed`.
- The new hostname passes the same hostname checks as create.
- Everything inside Actual is copied, including users, passwords and OpenID settings, and the result says so. The OpenID settings name the source's hostname, so OpenID login on the clone needs them and the provider's redirect URL updated, and the result says that too, naming `https://<clone hostname>/openid/callback`.

## 8. Scheduled backups and Retention

### 8.1 The Nightly run

- One Host-wide `dcabsm-nightly.timer` starts a oneshot `dcabsm-nightly.service`, which runs `dcabsm host nightly`. `help` doesn't list that verb.
- It runs daily at the `nightly-time` setting, default 03:30 Host local time, which avoids the hour DST skips or repeats. `Persistent=true`, so a run missed while the Host was off happens at the next boot. There is no random delay, and `AccuracySec=1s` stops systemd's default one-minute accuracy from moving the run. The timer has an `[Install]` section with `WantedBy=timers.target`, so it can be enabled. Changing the setting regenerates the timer.
- It takes each Instance's `scheduled` Backup one after another, in alphabetical order, then applies Retention for that Instance. Running in sequence is the spacing, so only one Instance is down at a time.
- Setup installs and enables both units. They are owned files (10.5).

### 8.2 Instances during the run

- The lock is taken per Instance, not for the whole run, so an interactive command can slip in between Instances. The run waits up to 10 minutes for it, then skips that Instance as failed.
- An Instance with a `.changing-release` marker is skipped as failed.
- A stopped Instance is backed up without being started.
- An Instance that has never started has no data, so it is skipped, and that is not a failure.
- `backup schedule <name> on|off` sets `scheduledBackups`. An Instance with it off is still pruned by the same counts.

### 8.3 Retention

Counted per Instance and per kind, never by age.

| Kind | Kept by default |
|---|---|
| `scheduled` | newest 14 |
| `pre-upgrade` | newest 5, and the newest is never deleted whatever the setting |
| `pre-restore` | newest 5 |
| `pre-clone` | newest 5 |
| `manual` | all; never deleted automatically, deleting them is a Manual System Admin task |
| `final` | in `.removed-` folders, which Retention never touches |

- Each count is a Host setting (`keep-<kind>`), and none can be set below 1.
- In the Nightly run, Retention runs for an Instance only after its `scheduled` Backup succeeds. A failed Backup holds back pruning for that Instance that night, so a failing Instance never loses older Backups.
- `backup create`, `instance upgrade`, `instance restore` and `instance clone` never prune.
- `backup prune [<names>|--all] [--dry-run]` applies the same rules by hand.
- DCABSM never deletes Backups early to make room.

### 8.4 Failures

- The run carries on past a failed Instance, logs to journald, ends with a summary and exits non-zero, so the unit shows as failed in `systemctl`.
- `instance list` and `doctor` warn when an Instance with scheduled Backups on has no `scheduled` archive newer than 48 hours, unless the Instance itself is younger than 48 hours by its `createdAt`, since no Nightly run is due yet. An Instance with no `createdAt` is treated as older. This catches a failing schedule and a disabled timer alike, read from the directory listing with no state file.
- `doctor` warns when free space on the backup filesystem is below the total size of the newest Backup of each Instance with scheduled Backups on, meaning the next Nightly run wouldn't fit. Only those Instances count, because the Nightly run backs up no others. If the free space can't be read, `doctor` warns that it couldn't measure instead of saying nothing.

## 9. Command-line behaviour

The full command surface, prompts and messages are in [docs/cli.md](../cli.md). The rules:

- Commands are `dcabsm <noun> <verb> [args] [flags]`, under `host`, `instance`, `backup`, `cert`, `release` and `self`. There are no flat verbs and no short aliases.
- Every command that changes an Instance or causes an outage is an `instance` verb. `backup` only handles archives.
- Every command requires root, usually through `sudo`. Anything else exits at once with one clear message. There is no helper, setuid binary or admin group. The exceptions are `help`, `dcabsm --version` and `self version`, which change nothing.
- Every command except `host setup`, `self update` and those three refuses until `/etc/dcabsm/dcabsm.json` exists, and points to setup.
- One declarative noun → verb table drives `help`, routing and the bash completion script, which is generated from it at build time, with a test that the two match.
- Destructive commands confirm by typing the Instance name. Scripts pass `--confirm <name>`. Other prompts take `--yes`. A prompt with no terminal and no flag refuses.
- Errors print one line, then an indented hint giving the full next command.
- Exit codes: `0` success, `1` failure or cancel, `2` usage error or a refusal before anything changed. `host doctor` has its own: `0` pass or notes, `1` warnings, `2` any failure.
- Ordinary commands never use the network. Only `host check-updates`, Release and Node installs, `instance upgrade` and `self update` do.

### 9.1 Tab completion

- bash completion ships in V1, installed by `install.sh` and `self update` to `/usr/share/bash-completion/completions/dcabsm` as an owned file.
- `sudo dcabsm <Tab>` works through bash-completion's `sudo` handling.
- It completes nouns, verbs, flags, Instance names and Release versions, by listing `instances/` and `releases/` without root. Backup archive names don't complete, because `backups/` is root-only.
- `doctor` notes a Host without the `bash-completion` package.

## 10. Host setup and doctor

### 10.1 One list of checks

Setup and doctor share one list of checks. Each check has a test, a severity and an optional fix. Setup runs the Host checks and applies their fixes. Doctor runs the Host and Instance checks. Every check can run unattended.

### 10.2 Setup

`host setup [--release <v>] [--backup-dir <path>] [--yes]`, in order:

1. Require root and take the lock.
2. Run every check that can refuse (10.3), before anything changes, and find drifted files.
3. Show the plan and confirm, unless `--yes`. On TurnKey, the plan lists what setup will disable (10.7), and this one confirmation covers it.
4. On TurnKey, disable those pieces.
5. Install the distro's `nginx`, `openssl` and `xz-utils` with apt. `xz-utils` unpacks Node's tarballs, and TurnKey Core does not ship it.
6. Create `/etc/dcabsm/dcabsm.json`, with the layout version, and the `/srv/dcabsm` tree, including `node/` and `acme/`. `--backup-dir` sets `backupDir`, with no prompt. On a re-run, a `--backup-dir` that differs from the stored `backupDir` is refused, because moving Backups is a Manual System Admin task.
7. Write `dcabsm@.service`, the `dcabsm-nightly` units and the `conf.d` files. Run `nginx -t`, start and enable Nginx (asking first if it was installed but stopped), and reload. Enable the timer.
8. Install the latest stable Release, or `--release <v>`, with its Node runtime, and confirm its native modules load. This check passes once any Release loads, so a re-run never pulls a newer one.
9. Print a summary that ends with the next step, creating an Instance.

Setup is safe to re-run. It does only what's missing and has no undo. A failure stops it with the reason, and a re-run carries on. It never touches an Instance.

### 10.3 Refusals

| Found | Outcome |
|---|---|
| OS or architecture not in the table in 1.4, read from `/etc/os-release` | Refuse, no override |
| A TurnKey appliance other than Core or Node.js | Refuse, no override: "Only TurnKey Core and Node.js are supported. Use one of those, or plain Debian 13." |
| The Proxmox VE host itself | Refuse, no override, suggest a VM |
| A container (LXC, WSL, Docker, Podman) | Refuse; `DCABSM_ALLOW_CONTAINER=1` passes, for tests only |
| nginx.org's package, installed or apt's candidate | Refuse; `DCABSM_ALLOW_NGINX_ORG=1` passes |
| Nginx forks, source builds, or anything else on 80 or 443 | Refuse, no override, naming the process |
| An existing Nginx config that fails `nginx -t` | Refuse, showing the error, as a Manual System Admin task |
| TurnKey's first-boot setup not finished (10.7) | Refuse, no override, pointing to TurnKey's first-boot setup |

nginx.org's package would very likely work, since DCABSM only writes to `conf.d`. It is unsupported to keep the test matrix to one Nginx version per OS.

If the Host later runs an unsupported OS, only setup refuses. Every other command keeps working, warning and logging each time, and doctor fails, so Backup and restore still work after a risky OS upgrade.

### 10.4 Overrides and the Unsupported Host mark

Any override prints a loud unsupported, at-your-own-risk warning on every run, logs its use to journald, and leaves a permanent mark in `dcabsm.json`, which makes the Host an Unsupported Host for good, even after the override is gone. `instance list` and `doctor` always show the mark.

### 10.5 Owned files and drift

The owned files are `dcabsm@.service`, `dcabsm-nightly.timer`, `dcabsm-nightly.service`, `dcabsm.conf`, `dcabsm-default.conf`, each `vhost.conf` and the bash completion script. `dcabsm.json` records a hash of each one DCABSM last wrote.

- A file that still matches its hash is DCABSM's own older output, and setup, doctor and Self-update replace it without asking.
- A file that differs was edited by the System Admin. It gets a diff and a choice: replace, which saves the old copy to `/etc/dcabsm/replaced/<timestamp>/`, or keep, which leaves a warning that doctor keeps raising.
- With no terminal, `--yes` replaces, and its absence stops before any change, listing the files.
- Every Nginx file change runs `nginx -t` before reloading.

### 10.6 Doctor

`host doctor` is read-only and takes no lock. It says so if the lock is held. `host doctor --fix` takes the lock and asks fix or skip for each problem, with an all option, diffs for files and old copies saved as in 10.5. `--yes` fixes everything. No terminal and no `--yes` refuses.

`doctor --fix` fixes only what DCABSM owns. The one exception is the three TurnKey pieces in 10.7.

| Check | Doctor |
|---|---|
| Supported OS and architecture, not Proxmox VE, not a container. The OS line names the OS, for example "TurnKey Node.js 19.0 (Debian 13)" | Reports |
| Unsupported Host mark | Always shown |
| Nginx from the distro, judged by the installed package's origin; apt's candidate from the distro; nothing foreign on 80 or 443 | Reports |
| On TurnKey, a disabled piece (10.7) is back | Warns, and fixes after asking |
| On TurnKey, `webmin-nginx` is installed | Notes |
| Nginx running and enabled | Fixes |
| `nginx -t` passes | Reports |
| Owned files present and matching (10.5), timer enabled | Fixes |
| Another default server on 443 | Reports |
| `/etc/dcabsm` and `/srv/dcabsm` ownership and modes | Fixes |
| Every Release loads its native modules | Reports, points to `instance upgrade` |
| Node runtime has a newer patch, or its major is end of life | Reports, points to `release update-node` |
| Leftover `.installing-*` folders | Fixes (deletes) |
| `dcabsm-*` accounts with no Instance | Fixes (deletes) |
| `.removed-` backup folders, with their size | Reports |
| Backups share a disk with Instance data | Reports; only a note when it is the one disk on the Host |
| Backup filesystem lacks room for the next Nightly run | Warns |
| `bash-completion` package missing | Notes |
| Firewall active without 80 and 443 allowed | Reports, as a Manual System Admin task |
| Instance `config.json` matches its record | Fixes, then asks separately to restart; otherwise reports "restart needed" |
| Instance `vhost.conf` matches | Fixes, with `nginx -t` and reload |
| Instance settings the current Release doesn't use (4.11) | Notes |
| Instance ownership, and its account exists | Fixes, recreating the account if missing |
| Certificate test (5.7) | Reports |
| Instance port used by something else or by another record | Reports |
| Running version from `/info` matches the Instance's Release | Reports |
| No `scheduled` archive newer than 48 hours, with scheduled Backups on and the Instance older than 48 hours | Warns |
| `.changing-release` marker | Reports, points to `instance rollback` |

**Severities.** A failure (exit 2) is something that stops an Instance or its Release running: a missing Instance account, a port conflict (two records on one port, or another process on an Instance's port), a Release's bad or missing `node` link, and an Instance with no `release` link. A warning (exit 1) is drift that `--fix` can mend or the System Admin can act on: `config.json` or `vhost.conf` differing from the record, wrong ownership or modes, a missing directory, a missing `cert.pem` or `key.pem`, a unit that is active but whose `/info` doesn't answer or reports another version, a late scheduled Backup, too little room for the Nightly run, a restart that is needed, and a probe that couldn't measure. A note (exit 0) is information only: settings the current Release doesn't use.

**Instance check details.**

- An Instance with a `.changing-release` marker (6.6) isn't judged on `config.json` or `vhost.conf`, because rollback rewrites them. The marker check reports it.
- An Instance with no `release` link can't have its `config.json` checked. That is a failure, and the hint points to `instance restore`.
- A running Instance whose `config.json` matches its record but is newer than the unit's start is reported as "restart needed". Doctor compares the file's modification time with the unit's `ActiveEnterTimestamp`. If systemd gives no start time for an active unit, doctor warns that it couldn't measure.
- A unit that is active but doesn't answer `/info` on its port is a warning. A stopped Instance isn't asked.
- A missing `cert.pem` or `key.pem` is a warning with a pointer to `cert update`. `--fix` doesn't recreate them, since DCABSM can't invent a certificate.
- Port checks have blind spots, chosen to avoid wrong accusations. A running unit with no `MainPID` is left alone, because nothing says the listener is foreign, so a real conflict during start-up can be missed. If `ss` can't be run, the "in use by" check is skipped, and the check of two records on one port still runs. Only each Instance's own recorded port is looked at.
- When `--fix` writes a `vhost.conf`, the old copy is saved before the new one is written, even if `nginx -t` then fails and the old file is put back (10.5).

DCABSM never changes firewall rules. Other Host hardening, such as SSH and automatic security updates, is out of scope.

### 10.7 TurnKey Linux

TurnKey Core 19.x and TurnKey Node.js 19.x, on Debian 13, are supported Hosts when installed from the ISO in a VM or on bare metal. They are not Unsupported Hosts. TurnKey's LXC templates are refused as containers.

**Detection.** Setup and doctor read `/etc/turnkey_version`, for example `turnkey-nodejs-19.0-trixie-amd64`, and confirm it against the matching `turnkey-<name>-<version>` package, for example `turnkey-nodejs-19.0`. Any other appliance is refused before anything changes (10.3).

**First boot.** Until TurnKey's first-boot setup finishes, its headless "init fence" redirects remote 80 and 443. Setup refuses until it has finished (10.3). Setup and doctor tell it has finished when both hold, read from TurnKey's inithooks sources:

- `RUN_FIRSTBOOT=false` in `/etc/default/inithooks`. The last first-boot hook, `98finalize`, sets it.
- `turnkey-init-fence.service` is not active. On an ISO install the hook `97turnkey-init-fence-disable` stops it; a headless build keeps it up until the first root login, which is why the flag alone is not enough.

**Needs confirming on the lab VM (13.4):** this was derived from the sources, not observed on a booted appliance.

**What setup disables.** These clash with DCABSM. Setup explains them, asks once as part of its plan (`--yes` answers), then disables them. Nothing is deleted.

| Piece | Appliance | How | Why |
|---|---|---|---|
| `/etc/nginx/sites-enabled/nodejs` | Node.js | remove the link | It is the 443 default server, so DCABSM's catch-all (5.3) would be skipped, and it sends a two-year HSTS header, which breaks a self-signed click-through |
| `pm2-node.service` | Node.js | disable and stop | It runs TurnKey's sample app behind that site |
| `/etc/cron.daily/confconsole-dehydrated` | either, if present | remove its executable bit | confconsole's Let's Encrypt renewal stops Nginx, taking every Instance down |

On Core with no renewal job, there is nothing to ask. If any piece comes back, doctor warns and `doctor --fix` disables it again after asking. This is the one written exception to "`doctor --fix` fixes only what DCABSM owns".

**Left alone.** Webmin, Postfix, TurnKey's firewall (it already allows 80 and 443), confconsole, inithooks and TurnKey's apt sources. TurnKey's apt repo is pinned at 999, so a future TurnKey `nginx` package would replace Debian's, which is why doctor checks the installed package's origin (10.6). confconsole's Let's Encrypt must not be used with DCABSM. Webmin must not be used to edit Nginx files.

## 11. Installing and updating DCABSM

DCABSM ships as a signed tarball with its own Node ([ADR-0003](../adr/0003-signed-tarball-with-its-own-node.md)).

### 11.1 What ships

- The repo and its releases live on GitHub. DCABSM uses semver, kept apart from Actual's calendar versions. It is not published to npm.
- Each GitHub Release publishes `dcabsm-<ver>-linux-amd64.tar.gz` and `dcabsm-<ver>-linux-arm64.tar.gz`, each holding the bundled JS and a pinned official Node, plus `install.sh`, `SHA256SUMS` and `SHA256SUMS.sig`.
- DCABSM's own Node is not one of the managed Node runtimes, so setup can run before any exists. It gets patches only through new DCABSM versions, which is acceptable for a CLI that never listens on a port.
- Each tarball holds one top-level folder with `bin/dcabsm`, `share/bash-completion/completions/dcabsm`, the bundled JS and the pinned Node. The README's by-hand steps rely on this.
- Versions sit in `/opt/dcabsm/<ver>/`, and `/usr/local/bin/dcabsm` links to the current one. Only the current and the previous version are kept.

### 11.2 Signing

- The author signs `SHA256SUMS` with an OpenPGP key on their own machine, never in CI, so a compromised GitHub account or CI run can't sign.
- The fingerprint is published only in the README and on `keys.openpgp.org`.
- DCABSM checks signatures with `gpgv`, which every supported OS already has, for its own releases and for Node's.
- Self-update checks only against the key already installed, never one from the download, so later updates are protected even if GitHub is compromised.
- A new key ships inside a Self-update signed by the old one. The key has a long expiry that is extended before it lapses.
- A lost or revoked key means a README notice and a manual reinstall with the new key on every Host.

### 11.3 First install

`install.sh`, run with `sudo bash install.sh` after reading it:

1. Check the OS and architecture.
2. Print the key fingerprint and ask the System Admin to compare it with the README or `keys.openpgp.org`. `--yes` skips the question.
3. Download the tarball, `SHA256SUMS` and `SHA256SUMS.sig`, and check them with `gpgv`.
4. Extract to `/opt/dcabsm/<ver>/`, create the symlink and install the completion script.
5. Print "next: `sudo dcabsm host setup`".

It never runs setup and never touches apt. If DCABSM is already installed, it points to `sudo dcabsm self update` and stops, changing nothing. The README lists the same steps by hand.

### 11.4 Self-update and stored state

`self update [--to <ver>]` is explicit and takes the lock. Nothing updates automatically, and only stable versions are offered.

1. Fetch the latest version, or `--to <ver>`, and check it against the installed key.
2. Extract it to `/opt/dcabsm/<new>/`.
3. Run the new version's layout migrations, if any.
4. Switch the symlink and bring the owned files up to date (10.5).

- It never restarts Instances. When an Instance's generated config changed, it reports "restart needed", as doctor does.
- `--to <ver>` moves to any version, older or newer, only when the layout version is the same. `--to` the running version, with a lower stored layout, migrates in place.
- Without `--to` it takes the latest version. If that is the running version, it reports up to date; if it is older, it refuses as "ahead of the latest". Going down needs an explicit `--to`.
- Each DCABSM version knows the layout version it expects. If the stored one is lower, every command refuses except the migration inside Self-update, which runs under the lock after copying `/etc/dcabsm` aside. If a migration fails, or any later step of the update does (the symlink switch, the refresh), the copy goes back, the new version is removed and the symlink stays on the old version. Migrations only go forward.
- If the stored layout is higher, every command refuses and names the DCABSM version needed.
- `self version` and `dcabsm --version` print the installed version.

### 11.5 Removal

V1 has no uninstall command. Removing `/opt/dcabsm`, the symlink and the completion script is a Manual System Admin task documented in the README. Instances, Releases and Backups stay.

## 12. Known limits and untested areas

These are recorded so the test plan covers them and the docs don't overpromise. Each is either tested before V1 ships, through the layers in section 13, or stays a documented limit.

### 12.1 Tested before V1

- **Real systemd and Nginx.** The sandbox was first tested on Debian 13 arm64 in a privileged container, and the Nginx front by running Nginx directly on arm64. Before V1 the lab VMs (13.4) cover Ubuntu 24.04 and 26.04, the sandbox on real amd64, reboots, `systemctl reload nginx` and real remote clients.
- **Read-only Releases** were first run on emulated amd64 without systemd. The lab VMs run them on amd64 under systemd.
- **Host setup and doctor** were untested. They are a first-class part of the journey in every layer.
- **`instance reset-password` on a live server**, including SQLite busy behaviour, was read from source, not run. The container layer runs it on a live server, with a busy SQLite, scripted through a pseudo-terminal.
- **Actual's server routes.** `/health` and `/info` aren't a documented public API. The pinned container tests and the weekly live job (13.3) catch a change.
- **Regroup with end-to-end encrypted budgets** is untested. The key and the messages are kept, so it should work. It is tested by hand once.
- **Browsers.** Device behaviour after a Release change and a restore was tested in Chromium only. Firefox and Safari on a Mac are tested by hand once, in one pass of the browser checklist against the lab.
- **TurnKey Core and Node.js** were researched from TurnKey's sources, not booted. A lab VM tests both (13.4).

### 12.2 Documented limits

- **Restore is DCABSM's own approach.** Actual doesn't document or support restoring a server from its files.
- **Mobile browsers** are untested.
- **arm64** is built and CI-tested, but not tested on a real Host (1.4).
- **Raspberry Pi OS** is expected to report itself as Debian 13, but that is unconfirmed.
- **IPv6 listeners** are untested.
- **Local budget copies across client migrations.** 26.10.0 and 26.11.0 share the same budget migrations, so a client migration between Releases hasn't been tested. Clients re-upload their whole file on open every 7 days, so a client migration can reach server data within a week.
- **Instance isolation** covers files and processes, not localhost ports (4.12). This is a design limit.
- **Self-signed certificates** work after clicking through, but without a service worker, so no offline start and no install as an app. How long a browser remembers the click-through is unconfirmed: Chromium normally forgets it after about a week.

## 13. Testing

### 13.1 Layers

1. **Unit**, on the author's machine and in CI, with no root, systemd or network. Every path (`/srv/dcabsm`, `/etc/dcabsm`, the `conf.d` include) hangs off one configurable root, so tests use a real filesystem under a temporary root and assert on the files left behind, because the filesystem is the only record ([ADR-0001](../adr/0001-filesystem-is-the-only-record.md)). Only two seams are faked:
   - a **command runner**, for `systemctl`, `nginx -t`, `useradd`, `runuser`, `apt`, `gpgv` and `npm`
   - a **fetcher**, for npm, nodejs.org, GitHub, and Actual's `/health` and `/info`
2. **Container integration**: systemd as PID 1, one image per supported OS, running the real `dcabsm` as root with real Nginx, accounts, npm installs and the sandbox.
3. **VM end-to-end**: one lab VM per supported OS, for reboots, the sandbox outside a privileged container, `install.sh` from a fresh image and `systemctl reload nginx` under real systemd.
4. **Manual browser checklist**, for device behaviour after an Upgrade, rollback, restore and Clone.

### 13.2 Containers are a test tool only

Setup refuses containers (10.3), so every container run sets `DCABSM_ALLOW_CONTAINER=1`, and the journey expects `host doctor` to report the Unsupported Host mark. One test checks that setup refuses in a container without the override.

The test containers are privileged and built for the tests, unlike the unprivileged LXC or systemd-less Docker that users run, where the sandbox and the systemd design break. Container runs never count as evidence of support, and the public docs never cite them as such. There are no TurnKey container images.

### 13.3 CI

The repo is public, so GitHub's standard hosted runners are free, arm64 included. Larger runners are never used. If the repo ever starts private, the arm64 jobs wait until it is public.

- The author tests locally first.
- Pull requests, pushes to `main` and version tags run the unit and completion tests, build both tarballs, and run the container layer for all three OS images on native amd64 (`ubuntu-24.04`) and arm64 (`ubuntu-24.04-arm`) runners.
- **Pinned Actual packages.** A pinned set of Releases (26.10.0, 26.11.0 and the latest supported) and their Node tarballs are fetched once, cached, and served to `dcabsm` from a local static server, so runs repeat and still exercise the real install path.
- **Weekly live job.** A scheduled job installs the newest Release and Node from the live sources, so a new Release that breaks install, `/health`, `/info` or a migration shows up before a user hits it.

**Completion test.** A behavioural test generates the completion script from the command table, loads it into real bash 5 with bash-completion, and checks `COMPREPLY` for every noun, verb and flag path, for Instance names and Release versions from fixture `instances/` and `releases/` without root, and for `sudo dcabsm <Tab>`. It runs in CI and the containers, and is skipped on macOS's bash 3.2.

### 13.4 The lab

A private, in-house set of amd64 VMs, one per supported OS: Debian 13, Ubuntu 24.04, Ubuntu 26.04, and one TurnKey VM with two snapshots, `clean-core` and `clean-nodejs`, each a fresh ISO install. Every other VM has a `clean` snapshot.

- Generic scripts in the repo, for example `scripts/remote-test.sh <os>`, roll a VM back to its clean snapshot, copy the CI-built tarball over by SSH alias, run `install.sh`, then run a scripted journey: Host setup, two Instances, Upgrade, rollback, Backup, restore, Clone, reboot and `host doctor`.
- On TurnKey the journey adds: the setup prompt, the `nodejs` site disabled, DCABSM's catch-all as the default server, no HSTS on an Instance, and doctor's TurnKey warnings.
- The scripts run by hand from the author's machine, never in CI, so CI holds no credentials.
- **No lab details live in the repo.** Every lab detail (API URL and token, VM ids, SSH aliases, hostnames) lives in `~/.config/test-vms.env`, mode 600, outside the repo. The repo's example file uses `.invalid` placeholders and never holds a real hostname, IP, VM id or token.
- Public docs say only what DCABSM was tested on, never the lab's specs.

### 13.5 Release gate

The author signs only the exact CI-built tarball that passed:

1. Green CI on the tagged commit.
2. The VM journey on every lab VM and snapshot, from clean.
3. `self update` from the previous DCABSM version on at least one VM.
4. The browser checklist, only when the release changes Upgrade, rollback, restore, Regroup or the Nginx vhost.

### 13.6 OS gate

An OS joins the supported table in the code (1.4) only after:

1. its image is in the container matrix on both architectures, where the OS publishes both
2. a lab VM with a clean snapshot exists
3. the full VM journey passes on it
4. the browser checklist passes once against it

The V1 OSes go through the same gate, so none ships untested. TurnKey has no container image, because its pieces are tested on the lab VM.

## 14. Open items

A review of the package against every design ticket on 2026-11-09 found gaps. The user's decisions on them are in the sections above. These are left to the implementation ticket that owns the named section, and each is a requirement on that ticket.

- **Setting the first password from the CLI** (4.6). Checked in Actual's source on 2026-11-09 (`bin/actual-server.js`, `src/scripts/reset-password.js`, `src/account-db.js`, `app.ts`). **Finding: not on a never-started Instance.** The reset script does set a first password when the `auth` table is empty (`needsBootstrap()`), but it never runs Actual's migrations, which run only in `app.ts` at server start, so on an Instance with no `account.sqlite` the `auth` table doesn't exist and the script fails. It works once the server has started at least once, which is the same window the browser has. So `instance create` can't offer it before the first start, and `instance reset-password` keeps refusing a never-started Instance. **Decided:** `instance create` offers the reset after Verification, on a terminal only (4.6 step 8).
- **TurnKey's first boot** (10.7). Implemented from TurnKey's inithooks sources (`RUN_FIRSTBOOT=false` and `turnkey-init-fence` inactive); still to be confirmed on the lab VM.
- **Release-time placeholders.** The GitHub owner in release URLs and the key fingerprint in the README and `docs/cli.md`. After the Firefox and Safari pass (12.1), the "Here be dragons" lines in the README and `docs/cli.md` need updating.
